# devhelp-platform — agent guide

Monorepo for devhelp.pk: a free, open-source learning platform (marketing site + LMS) for software engineers and students in Pakistan. `CLAUDE.md` is a symlink to this file; keep guidance here only.

## Commands (run from repo root)

```sh
pnpm install                     # Node 24, pnpm 11 (see .nvmrc / packageManager)
cp .env.example .env && pnpm db:up && pnpm db:migrate && pnpm db:seed   # db:up also starts Mailpit (:8025) and MinIO (:9000, console :9001)
pnpm content:refresh             # pull the pinned devhelp-content commit, check it, sync metadata into Postgres
pnpm dev                         # web :3000, lms :3001 (Mailpit UI :8025 for local email)
pnpm format && pnpm lint && pnpm check-types && pnpm test && pnpm build   # must all pass before a commit
pnpm --filter <pkg> <script>     # target one workspace, e.g. pnpm --filter @repo/database db:generate
```

Turborepo scopes tasks to the package of the current working directory. Always run `turbo` / `pnpm <task>` from the repo root, or you will only run one package's tasks and read the "Tasks: N successful" line wrong.

## Type safety (non-negotiable, requirement X10)

- Entity types are Drizzle-inferred (`typeof table.$inferSelect`); never hand-write a row type.
- Every `jsonb` column has a Zod schema in `packages/database/src/schema/json.ts`; the column's `.$type<>()` uses the type inferred from that schema. Validate with it at every write boundary.
- Learner progress is written only through `recordEvent` / `enroll` from `@repo/learning` (Zod-validated, transactional, idempotent). Never insert into `progress_events`, `lesson_progress`, or `enrollments` directly outside that package. `rebuildLearner(userId)` replays the stream.
- Client-facing APIs go through tRPC v11 in `packages/api`: React Query hooks on the client (`useTRPC()` from `@/lib/trpc/client`), the server caller `api(headers)` from `@repo/api/server` in RSC. No untyped `fetch` to our own routes. `typedRoutes` is on in both apps: cast dynamic hrefs with `as Route` (from `next`), never `as never`.
- Env is validated by `@repo/env` (`env` = full server schema, `@repo/env/client` = `NEXT_PUBLIC_*`, `@repo/env/database` = the DB-only slice used by drizzle-kit and the seed). Public URLs default to localhost only outside production; both apps inline them from the validated env in `next.config.ts`. `SKIP_ENV_VALIDATION=1` bypasses validation for one-off scripts. `packages/content` reads `process.env` directly so `content:pull` works on a fresh clone.
- Quiz answers never reach the browser: read questions through `questionPublicColumns` + `toPublicOptions`.
- `packages/auth` and `packages/learning` set `declaration: false` because Better Auth / Drizzle inferred types are not portable; keep that when adding packages that re-export them.

## Content pipeline (S2)

- Curriculum lives in the public repo `devhelppk/devhelp-content` (MDX + YAML, CC BY-SA). `content.lock.json` pins the commit the platform builds against. `pnpm content:pull` downloads that sha into `.content/` (gitignored); `pnpm content:check` validates it (schema, refs, links, quiz answers, exercise tests against `solution/`); `pnpm content:sync` upserts metadata by slug and records a `content_revisions` row. `pnpm content:refresh` does all three.
- While authoring, set `CONTENT_DIR=../devhelp-content` to use a sibling checkout instead of the tarball; `pnpm content:check ../devhelp-content` works from the repo root (paths resolve from `INIT_CWD`).
- Lesson bodies are compiled at build time by Content Collections (`apps/lms/content-collections.ts`) and looked up by `lessons.content_path`; they are never stored in Postgres. New content therefore needs a platform rebuild; the promote workflow in the content repo opens a lock-bump PR on merge.
- `POST /api/content/sync` (admin session or `CONTENT_SYNC_SECRET` bearer) re-runs the sync for the deployed content. It is a recovery tool, not a publish path.
- Sync archives (never deletes) rows missing from content, and only rows previously produced by the same repo, so a sync from a fixture or another source cannot archive real content.
- `@repo/content-schema` uses explicit `.ts` import extensions because Content Collections loads it through Node's native TS loader; consumers set `allowImportingTsExtensions`. Content Collections rejects function-form schemas: pass a Zod object (loose) and do strict validation in `transform`.

## Conventions and gotchas

- **Design system first.** Read `packages/ui/DESIGN.md` before adding UI. Use existing tokens (`bg-primary`, `text-muted-foreground`, `brand-600`, `madder-600`) rather than raw colours. Do not restyle scrollbars per component; the thin themed scrollbar is global.
- **Adding shadcn components:** `cd packages/ui && pnpm dlx shadcn@latest add <name> --yes`. The CLI sometimes writes `import { cn } from "cn"` and adds a bogus `cn` dependency. Fix the import to `@repo/ui/lib/utils` and `pnpm remove cn` from `packages/ui` after every add.
- **Brand mark:** use `BrandMark` / `BrandLogo` from `@repo/ui/components/*`. Static SVGs live in `packages/ui/src/assets/brand/`; app favicons are `app/icon.svg`.
- **Internal links in apps must use `next/link`.** ESLint runs with `--max-warnings 0` and `@next/next/no-html-link-for-pages` fails the build on `<a href="/...">`.
- **TypeScript 7:** `baseUrl` is removed. Use `paths` alone (`"@/*": ["./*"]`).
- **Drizzle-kit prompts:** when a table both gains and loses columns, `pnpm db:generate` asks interactively whether each new column is a rename (first option, Enter = create). It needs a TTY; from an agent shell drive it through a pty (see `scratchpad/drive-generate.py` pattern) or run it in a real terminal. Hand-edit the SQL when a new NOT NULL column needs a backfill (add nullable, UPDATE, SET NOT NULL).
- **Database:** write `camelCase` columns in Drizzle; `casing: "snake_case"` is set in both the client (`src/index.ts`) and `drizzle.config.ts`, so Postgres columns are `snake_case`. Keep both in sync. After a schema change run `pnpm db:generate`, rename the generated file to something descriptive (update `drizzle/meta/_journal.json` `tag` to match), then `pnpm db:migrate`. `db:push` is for throwaway prototyping only. Commit migrations.
- **Auth schema:** identity tables come from the Better Auth config. Change `packages/auth/src/server.ts` (e.g. `additionalFields`), then `pnpm --filter @repo/auth auth:generate` (writes `packages/database/src/schema/auth.ts`), then `pnpm db:generate` + `pnpm db:migrate`. Use the `auth` CLI package (matches `better-auth` 1.7); `@better-auth/cli` is stale at 1.4 and emits an incompatible schema. Route handlers live at `app/api/auth/[...all]/route.ts` in each app.
- **Auth tests** in `packages/auth` hit the real local Postgres and need `BETTER_AUTH_SECRET` in `.env`.
- **Env:** `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, optional `GITHUB_*` / `GOOGLE_*` OAuth keys, `EMAIL_PROVIDER` + `EMAIL_FROM` (+ `RESEND_API_KEY` or `SMTP_URL`). `packages/database/src/env.ts` walks up to the repo root `.env` (marked by `pnpm-workspace.yaml`) so apps, drizzle-kit, and the seed all share it. Declare new env vars in `turbo.json` `globalEnv`.
- **Tests:** Vitest + Testing Library. UI and app tests use `@repo/vitest-config/ui` (jsdom, `vitest.setup.ts` loads jest-dom). Node packages use `@repo/vitest-config/base`. Co-locate tests as `*.test.ts(x)`.
- **Formatting:** Prettier with the Tailwind class-sorting plugin; run `pnpm format` before committing. CI runs `format:check`.
- **Ports:** web 3000, lms 3001. Stop dev servers with `pgrep -f "next dev" | xargs -r kill`; `pkill -f "next dev"` will match and kill the invoking shell.
- **Progress event keys carry the enrolment generation** (`:g<n>`, n = count of `course_enrolled` events) for lesson start/complete, and a mount-unique nonce for progress ticks, so a learner can re-do a course after dropping it and video sessions never collide.
- **Assessments.** Quizzes are graded only in `assessments.submitQuiz`; question reads go through `questionPublicColumns` + `toPublicOptions` and never include `isCorrect`, `answer`, `feedback`, or `explanation`. Exercise pass/fail comes from the browser and is recorded with the files; never execute learner code on the server. The runner's matcher subset is the contract for lesson tests; `content:check` and `content:sync` both enforce it (`parity` rule). Exercises are JavaScript/TypeScript only (founder decision at the end of S4); adding a language is a new spec, not a runner flag. Attempt limits are per quiz version; submissions take an advisory lock per (user, quiz/exercise); a `quiz_attempted` event re-evaluates course completion so a better retake can satisfy `minQuizScore`.
- **Web Workers must be `type: "module"`.** Turbopack bundles module workers into chunks but emits a classic worker's file as a raw asset, which only fails in production. Load runtime-only scripts through a runtime `import()` the bundler cannot see; after touching a worker, `pnpm build` and check `apps/lms/.next/static/chunks` for the worker chunk.
- **Lesson event keys** come from `lessonEventKey` and `enrolmentGeneration` in `@repo/learning`; do not mint `lesson_started:` / `lesson_completed:` keys by hand.
- **Moderation (S5).** Anything a person submits becomes a `moderation_items` row with a jsonb `payload` snapshot (Zod schema per subject type in `json.ts`); every status change writes a `moderation_actions` row in the same transaction. Use `mentorProcedure` + `moderatorTracks()` for queue reads (admins see all, mentors their `mentor_tracks`, track-less items are admin-only), `verifiedProcedure` for anything a learner contributes, and `rateLimit()` (Postgres counters) for per-user limits. Rejections carry a `policyClause` (`c1`…) that anchors into `docs/policy/content-policy.md`, rendered at `/policy` on the web app.
- **Email.** Never call Resend or nodemailer directly; go through `@repo/email`. Better Auth's verification, reset, and invitation mails are wired in `packages/auth/src/server.ts`. Tests run with `EMAIL_PROVIDER=log` (set by `@repo/vitest-config`); `pnpm db:up` also starts Mailpit (UI on :8025). Verification never blocks sign-in or learning; `verifiedProcedure` gates contributing.
- **Area 4 (S6).** Lesson feedback is private (`lesson_feedback`, one row per learner and lesson); course reviews are public and one per learner (`course_reviews`); discussions are `comments` with one level of replies. Markdown is rendered and sanitised on the server at write time (`packages/api/src/markdown.ts`: `marked` + `sanitize-html`, allow-list, `rel="nofollow ugc"`); never render learner Markdown on the client and never trust `bodyHtml` from input. Aggregates (`lessons.rating_avg/rating_count/unclear_count/open_question_count`, `courses.rating_avg/rating_count/review_count`) are recomputed by `recomputeLessonAggregates` / `recomputeCourseAggregates` from `@repo/learning` inside the writing transaction; never update them by hand. Links from accounts younger than 7 days hold the comment (`status = held`) and open a `comment` moderation item; the first flag on a visible comment or review creates its item; `applySubjectStatus` in the moderation router is the only place a decision changes a comment or review. The discussion island is `next/dynamic` with `ssr: false` so its text is never in server HTML.
- **Certificates (S7).** Issued by `issueCertificate` inside the reducer's `course_completed` case, one per learner per course, never deleted; `recordEvent` returns `certificateId` and announces it (notification + email) after the commit. The verify page `/verify/[uuid]` is public and cached; the PDF is rendered on first download by `apps/lms/app/api/certificates/[file]/route.ts` and cached in object storage under `certificates.pdf_key`; revoking clears the key so the next download carries the stamp. `pnpm certificates:backfill` issues for pre-S7 completions. Profile fields (`handle`, `profile_public`, `bio`, `links`) are Better Auth additional fields with `input: false`; only `account.updatePublicProfile` writes them.
- **Badges and streaks (S8).** Badges are content: `badges/*.yaml` syncs into the `badges` table like a course, and `content:check` validates the lucide icon name and the course or path a rule points at. Rules are evaluated by `evaluateBadges` inside `applyEvent`, so an award lands in the transaction that recorded the event and a replay is a no-op; awards and certificates survive `rebuildLearner`, `user_activity` does not (it is a read model). Days are Asia/Karachi through `ACTIVITY_TZ`; never compute a streak in UTC. There is no backfill: a badge published now applies from now on (founder, no users yet). `notify()` throttles emails per learner (4 an hour, 12 a day) and never drops the in-app row; pass `silent` for bulk work.
- **Company bank (S10a).** A company is a Better Auth organisation with `kind = "company"`; everything else about it lives in `company_profiles`, keyed by the organisation id, so the generated `schema/auth.ts` is never hand-edited. Companies are not content: they are created through Drizzle in `companies.propose` and the seed, never through the organisation plugin's endpoint, so `allowUserToCreateOrganization` stays restricted. Aggregates come from the `company_stats` **plain view** (migration 0013), declared in Drizzle with `pgView(...).existing()`; never recompute them by hand and never materialise it, because a moderator's decision must move the numbers at once. Public reads go through `reviewPublicColumns` / `interviewPublicColumns` only: `author_id` is never selected, and the month is computed at read time in Asia/Karachi (`to_char` over a timestamptz is stable, not immutable, so it cannot be a generated column; neither can anything using `array_to_string`). Contributions and proposals are decided by **admins only** in the ordinary moderation queue, with no track, so `scope()` already hides them from mentors. `cities` and `job_roles` are reference data seeded by `pnpm db:reference`, not content-repo files. Company pages read fresh on every request and are not cached: a cached-read layer was tried in S10a and removed because a hidden review stayed public for seconds after the decision.
- **Salaries (S10b).** Three rules in `salary_stats` and `salary_stats_detail` protect a contributor, and only together: `having count(*) >= 5`, rounding to a per-currency step, and withholding the quartiles below n = 8. The rounding is not cosmetic — `percentile_cont` lands exactly on raw values at n = 5, so the floor alone published three of those five people's real pay (found in the S10b review). Never relax any of the three, and never claim in a comment that an individual salary is unreachable: someone who knows four of five can still narrow the fifth. The views also exclude internships and anything older than three years, so a role's median is staff pay now rather than a blend. The only procedure that reads `amount_minor` from a row is `contributions.mine`, scoped to the caller's own point so they can check what they entered; never widen that. Money is stored in minor units with the currency it was earned in and a generated `monthly_minor` that divides a yearly figure by twelve; aggregates group by currency, and conversion is display-only. `fx_rates` is written by `pnpm fx:refresh` (a daily cron in production) and read from the table — never call an exchange-rate API on a request path, and render the page correctly when the table is empty. Unlike every other contribution a salary point publishes immediately and is marked unverified until an admin approves it, so its queue item allows `hide` from `pending`.
- **Flags and company marks (S10c).** One reason list, `FLAG_REASONS`, feeds every flag control; never hard-code a reason (S6 did, and moderators read "off topic" for everything). The company page's flag and report controls go through **server actions**, not `useTRPC`: it is a public, indexable page and the tRPC provider would ship to every reader for a control almost nobody touches. `/api/company-logos/<org id>` never 404s for a company — uploaded logo, then the site's own icon fetched server-side and cached in R2, then a generated monogram — so callers render an `<img>` unconditionally. Never hot-link a third-party favicon service; readers' browsers must not talk to anyone but us. Any server-side fetch of a company-supplied URL goes through `isSafeIconUrl` first, and every path that replaces a stored object must delete the one it replaced.
- **Who owns metadata (S11).** The content repo owns **what content is**: lesson bodies, quiz and exercise files, slugs, structure, `type`, `completionRule`, and the `video` / `quiz` / `exercise` reference that makes a lesson what it is. Postgres owns **how it is described**: titles, summaries, level, track, duration, cover image, publish state, and credits. `sync.ts` names the split in `COURSE_OWNED_BY_STUDIO` / `LESSON_OWNED_BY_STUDIO` / `MODULE_OWNED_BY_STUDIO` / `PATH_OWNED_BY_STUDIO` and passes updates through `repoOwned()`; a sync must never write those columns after the row exists, or the studio is pointless and the loss is silent. A new row is seeded with its slug as a placeholder title and `needs_metadata = true`, and cannot be published until a person describes it. A metadata key left in the repo fails `content:check` with `[moved-field]` naming where it went (`schemas/moved.ts`) — add to that map whenever a field moves. Credits are `content_credits` rows pointing at users, never handles in YAML, and every studio change writes a `content_edits` row in the same transaction.
- **Company claims and replies (S13).** A claim is a `company_claims` row plus a queue item; approving it inserts into `members`, and from then on **membership is the only question anything asks** — `isMember` in `routers/claims.ts`, never the claim table. Claims are their own row rather than a bare moderation item because `moderation_items` is unique on (subject type, subject id) and two people claiming one company would collide. Evidence is computed from the claimant's email domain against the company's website and **stored**, so a decision can be re-read as it stood; the suffix check compares against `"." + domain`, or `evilacme.com` claims `acme.com`. Approval inserts `role: \"member\"`, **never `owner`** — Better Auth's owner can rename, invite to, and delete the organisation, and deleting cascades away every review, interview, and salary point about that company. Hiding an approved claim deletes the membership, which is the only way to take representation back. A reply is one per post, queued like every other contribution, rendered and sanitised at write time by `renderMarkdown`, and once an admin hides it both its status **and its text** are frozen — freezing status alone let an edit smuggle unreviewed words onto the row for a later unhide to publish. Whenever a queue item is reopened, rewrite its `payload` too: the payload is what a moderator reads, and a stale one means approving text nobody saw.
- **Keep the LMS root layout thin.** Every provider there ships to every page; the tRPC provider is `LearnerProviders`, applied per page. The account menu is server-rendered (`<details>` + server action). Budget: 250 KB target / 300 KB ceiling first-load JS, enforced by `pnpm check-budget` against a running production server (CI does this after build).
- **Pages that read the session (`AccountMenu` calls `headers()`) or `searchParams` are dynamic**; do not add `revalidate` to them expecting ISR.
- **UI specs need the browser loop.** Any spec that touches UI is tested on the dev server in Chrome (all routes and states, light/dark, desktop and 390px), critiqued against `DESIGN.md`, fixed, and re-checked for at least two rounds before it is marked done; see `docs/spec.md`.
- **Scope discipline:** the LMS product surface (courses, lessons, progress UI) is intentionally thin until the research in `../research/` is acted on. Do not add domain-specific components to `packages/ui`; keep it generic.
