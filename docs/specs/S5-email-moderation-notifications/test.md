## Browser loop (Chrome, dev servers, Mailpit)

The signed-in flows were driven by a Playwright script against the installed Chrome (throwaway `@devhelp.test` accounts, emails read back from Mailpit's API, screenshots to disk); signed-out pages, the policy page, and the 404 page were checked in the Chrome session. Console clean on every page.

Flows: sign up → `/verify-email` → verification email in Mailpit → link → `/account` shows Verified → `/mentor/apply` (blocked and prompting to resend while unverified; form when verified) → application in review → admin (promoted by SQL, fresh sign-in) sees it in `/moderate` (admin-only badge), opens it, approves with a note → item shows Approved with the audit trail → applicant's header bell shows 1 → `/notifications` lists "You are now a mentor" → mark all read → organization created and the learner invited through the auth API → invitation email → `/accept-invitation/<id>` → accepted (member row present) → `/moderate` as the new mentor (empty: no tracked items yet) → forgot password → reset email → `/reset-password` → sign in with the new password. Themes: light and dark. Viewports: 1440 and 390 px with `scrollWidth <= innerWidth` asserted on `/notifications`, `/account`, `/moderate`, `/mentor/apply`.

Round 1 found: the organization endpoints refuse requests without an `Origin` header (test harness only); a role change is not visible until the session cookie cache (5 min) expires or the user signs in again, so the admin's queue 404'd right after promotion; every page overflowed by 3 px at 390 px because the header's Courses link, theme toggle, bell, and avatar no longer fit.
Round 1 fixes: the harness sends `Origin`; role-gated pages and procedures read the role fresh from the database instead of the cookie cache; the Courses link is hidden below `sm` (the account menu carries it).

Round 2: full loop re-run green, no horizontal overflow on any page, screenshots regenerated.

Round 3 (after code review, see `review.md`): the loop was re-run with the re-sign-in after the admin promotion removed; `/moderate` opened at once because the role is now read from the database. Better Auth's own `allowUserToCreateOrganization` still reads the session copy, so the harness refreshes the admin session before creating the organization (a real admin waits at most five minutes for that one check). Everything else unchanged and green; screenshots regenerated.

Screenshots (`docs/specs/S5-email-moderation-notifications/screenshots/`): `verify-email-pending`, `mentor-apply-unverified`, `account-verified`, `mentor-apply-pending`, `notifications-empty`, `moderate-queue`, `moderate-item`, `moderate-item-approved`, `moderate-queue-approved`, `header-bell-unread`, `notifications-unread`, `notifications-read`, `accept-invitation`, `moderate-as-new-mentor`, `forgot-password-sent`, `reset-password`, `notifications-dark-mobile`, `account-dark-mobile`, `moderate-dark-mobile`, `policy-dark` (all `.jpg`).

## Known limitations

- The account menu's Moderation link follows the 5-minute session cookie cache; the moderation pages and procedures themselves read the role fresh, so the link in the approval notification works at once.
- Resend was not exercised against the real API (no account yet; founder action). The transport is 30 lines over the official SDK and is selected by `EMAIL_PROVIDER`.
- The test accounts created by the loop remain in the local database (`*-<run>@devhelp.test`).
